StrictMath at SIMD speed: the same bits as Spark's exp, log and pow, up to 11.79× faster

In short. vfdlibm computes exp, log, pow and ten more functions on whole vectors of doubles, and every result has the same bits as java.lang.StrictMath, which Spark calls for exp, ln, power and their relatives. That matters because the bits differ elsewhere: on 32 test inputs on my Databricks Free Edition warehouse, Photon's results matched glibc's, not Spark's.

Faster, with the same bits

On the Intel Xeon Platinum 8573C (AVX-512), vfdlibm computes exp, log and pow up to 11.79× faster than StrictMath, and every result has the same bits.

These are timings of a loop over an array, not of a query: a query gains only as much as it spends in these functions. One function is not faster everywhere: on the AVX2 host, hypot is not shown faster than StrictMath, and on the benchmark's mixed data it is slower, with the same bits (a known issue of 0.3.0).

The method that uses vfdlibm is nine lines.

static final VectorSpecies<Double> S = DoubleVector.SPECIES_PREFERRED;

static void exp(double[] xs, double[] ys) {
  int i = 0;
  for (; i < S.loopBound(xs.length); i += S.length()) {
    VFdlibm.exp(DoubleVector.fromArray(S, xs, i)).intoArray(ys, i);
  }
  for (; i < xs.length; i++) {
    ys[i] = StrictMath.exp(xs[i]); // the tail that does not fill a whole vector
  }
}

The loop loads a vector of doubles from xs, computes exp of all of them at once, and stores the results in ys. The few doubles at the end that do not fill a vector go to StrictMath. "How I checked" has the whole program, which checks a million results against StrictMath.

Why your Spark job should care

When every engine returns the same doubles, a query gives the same answer after a migration, on a new cluster or on a new CPU, and a test that compares doubles does not flake (one kind of NaN aside, the first surprise below). StrictMath is how Spark gets there, and it computes one double at a time.

Spark's e is not Java's e

Spark computes exp with a different library than Java's Math, and you can see it in the last digits.

Ask Java for e and you get Math.E, 2.718281828459045. Ask Spark SQL for exp(1) and you get 2.7182818284590455. The two are neighbours: no double lies between them.

Spark's generated code calls java.lang.StrictMath for exp, ln, log10, power and their relatives, and java.lang.Math for the rest. The difference is a promise. Math.exp promises a result "within 1 ulp of the exact result", where an ulp, a unit in the last place, is the gap between a double and the next one. So it may return either neighbour, and the JIT, the compiler inside the JVM, may use code written for your CPU. StrictMath promises one algorithm, Sun's fdlibm 5.3, a C library, and follows it almost everywhere (the third surprise below). The same input gives the same 64 bits on every JVM and every CPU.

Photon returned other doubles on my warehouse

On a SQL warehouse of mine on Databricks Free Edition, Photon, Databricks' native query engine, returned results that matched the C library's, not Spark's.

I picked 32 inputs where StrictMath and glibc 2.43, the C library on my laptop, give different doubles, and ran them through Apache Spark on my laptop and through Photon on 24 November 2026. Spark matched StrictMath on every input. Photon matched glibc on every input. How often do the two libraries disagree? On my random inputs, about one exp in ten.

A second query adds the results up. For each of nine functions it takes a million inputs and returns an exact sum and a fingerprint of the results, so a change of one ulp in any row shows. Its plan on Databricks is Photon from end to end. On Spark and on Photon the inputs, their sums and their fingerprints agree, and so does the sqrt row, a control. Every other function's total differs. For seven of them, Photon's row equals, digit for digit, a prediction made from glibc 2.43 on my laptop.

One query shows it in two numbers. On the same warehouse on 25 November 2026, exp(1.0D) of a literal and exp(x) of a table holding 1.0, side by side, returned 2.7182818284590455 and 2.718281828459045. Spark's optimizer folds the literal on the driver, in the JVM, with StrictMath; Photon computes the column. On one engine, in one query, exp(1) has two values, depending on whether the 1 is typed or read from a table.

How vfdlibm keeps the bits

The Vector API (jdk.incubator.vector, still incubating in JDK 25) lets Java run one operation on several doubles at once. Each double in a vector is a lane. The vector's size is its species: a 512-bit species holds eight lanes.

vfdlibm ports fdlibm's C to that API. Version 0.3.0 has thirteen functions: exp, expm1, log, log10, log1p, pow, sinh, cosh, asin, acos, atan, atan2 and hypot.

A rare lane is one whose input sits at an edge of fdlibm's range, an infinity or a NaN. Six of the thirteen functions are the ones Spark computes with StrictMath; for the other seven Spark calls Math, and vfdlibm still returns StrictMath's bits. The one exception, a lane of two different NaNs, is the first surprise below.

Why not VectorOperators.EXP?

The Vector API has its own EXP, but it promises accuracy, not StrictMath's bits. Its Javadoc says floating point operations "follow the accuracy and monotonicity specifications of the equivalent Java operation or method", and EXP adds "Not guaranteed to be semi-monotonic." That is the kind of promise Math makes.

I measured its speed, and how often its bits differ from StrictMath's. It is faster: on common data, StrictMath takes 15.38 times as long as the operator on the Xeon and 6.95 times on the EPYC, and 6.73 and 4.12 times as long as vfdlibm in the same runs. On mixed data the operator is still ahead on the EPYC; on the Xeon the two are too close to call. But it does not keep StrictMath's bits. On my laptop, over the 200,000 random inputs of the bar chart above, the compiled operator differed from StrictMath.exp on 19,439 inputs at 128 and 256 bits and on 21,255 at 512 bits, each by one ulp. That is one laptop's count, but the answer changed with the vector width.

Why not Math.exp?

In the runs below, Math is faster than StrictMath for pow and for exp on common data (not shown for log), and Spark already calls it for sin and the rest. But it may return the other neighbour, as above: on the same 200,000 inputs, Math.exp differed from StrictMath.exp on 19,452, on my laptop. Is it at least faster than vfdlibm? I timed exp, log and pow all three ways, one run on each host. Math's time over vfdlibm's, common / mixed data:

The project reads a ratio under 1.3 as too close to call, and one from 1.3 to 1.4 from a single run as needing a re-run. So exp on the EPYC's mixed data and pow on the Xeon's are too close to call. On the EPYC's mixed data Math.pow is faster than vfdlibm, which takes 1.43 times as long; on its common data vfdlibm takes 1.30 times as long, which needs a re-run. In the other cells vfdlibm is faster, and it keeps StrictMath's bits.

Three surprises

1. StrictMath's NaN depends on the JIT

The same call can return a different NaN, depending on how far the JIT has compiled it.

A NaN, "not a number", carries spare bits, its payload. What should atan2 return when both of its arguments are NaNs with different payloads? This program, NanTier.java, asks two million times:

public class NanTier {
  public static void main(String[] a) {
    double x = Double.longBitsToDouble(0x7ff8000000000001L), y = Double.longBitsToDouble(0x7ff8000000000002L);
    long first = 0, second = 0, other = 0;
    for (int i = 0; i < 2_000_000; i++) {
      long r = Double.doubleToRawLongBits(StrictMath.atan2(x, y));
      if (r == 0x7ff8000000000001L) first++; else if (r == 0x7ff8000000000002L) second++; else other++;
    }
    System.out.println("atan2(NaN#1, NaN#2): first=" + first + " second=" + second + " other=" + other);
  }
}

One run each on my laptop, JDK 25.0.5.1 on x86-64 (your counts will differ):

$ java -Xint NanTier.java
atan2(NaN#1, NaN#2): first=2000000 second=0 other=0
$ java NanTier.java
atan2(NaN#1, NaN#2): first=1983613 second=16387 other=0

In the interpreter, every call returned the first NaN. With the JIT on, some returned the second. No code can match a target that moves. So in atan2, hypot and pow, a lane of two NaNs with different bits returns one of the two, quieted (for hypot, with the sign cleared too), and which one is not specified. Every other lane matches StrictMath bit for bit.

2. Fast code can quietly turn into slow code

When the JIT cannot keep a vector in CPU registers, it turns the vector into an object on the heap. That is called boxing. The results stay right, so every test still passes, but the vectors no longer stay in registers. Only the allocation shows it.

So the project's CI fails a benchmark that allocates. It also reads the machine code the JIT emits for every function and checks the register width, stray calls and fused multiply-adds. A fused multiply-add computes a * b + c with one rounding instead of two, which changes results, so none may appear.

3. StrictMath is not quite fdlibm

StrictMath and fdlibm agree almost everywhere, and a vector port has to match the JDK, not the C. On 24 November 2026, the nightly fuzzer found one input in about five billion where vfdlibm was one ulp below StrictMath.hypot.

Sun's C picks the larger argument by comparing the top 32 bits of the two only:

if(hb > ha) {a=y;b=x;j=ha; ha=hb;hb=j;} else {a=x;b=y;}

These two inputs share their top 32 bits, so the C keeps them in the order given, and its answer depends on that order. StrictMath.hypot gives one answer in both orders, on JDK 17, 21 and 25, and so does Math.hypot, which Spark calls. vfdlibm's port had followed the C exactly. In 0.3.0 it orders hypot's arguments by magnitude, so its result no longer depends on their order, as StrictMath's does not (#174).

What it does not do yet

sin, cos, tan, tanh and cbrt are not ported, and whether they will be is open. pow computes its common case in the vector and sends the rest to StrictMath.pow one lane at a time, pow(x, 2.0) and pow(x, 0.5) included. It needs JDK 25, where the Vector API is still an incubator module. On x86, code on 128-bit vectors calls the Vector API's Java fallback. And at SPECIES_MAX, only vectors of up to eight lanes are known not to allocate.

Try it

io.github.vecbricks:vfdlibm:0.3.0 is on Maven Central, and the source is at github.com/vecbricks/vfdlibm.

vfdlibm comes from Varka, my research fork of Apache Spark that compiles eligible SQL projections at runtime into one fused Vector API loop over Arrow buffers, and falls back to stock Spark on anything it cannot serve. To fuse exp, log or pow without changing a query's answer, Varka needs them with Spark's own bits, and vfdlibm is where they come from.

The example program

  • The dependency is io.github.vecbricks:vfdlibm:0.3.0 in a pom that compiles for Java 25 (the README has the whole pom), run with java --add-modules jdk.incubator.vector. The full program:
package example;

import io.github.vecbricks.vfdlibm.VFdlibm;
import jdk.incubator.vector.DoubleVector;
import jdk.incubator.vector.VectorSpecies;

public final class Main {
  static final VectorSpecies<Double> S = DoubleVector.SPECIES_PREFERRED;

  static void exp(double[] xs, double[] ys) {
    int i = 0;
    for (; i < S.loopBound(xs.length); i += S.length()) {
      VFdlibm.exp(DoubleVector.fromArray(S, xs, i)).intoArray(ys, i);
    }
    for (; i < xs.length; i++) {
      ys[i] = StrictMath.exp(xs[i]); // the tail that does not fill a whole vector
    }
  }

  public static void main(String[] args) {
    double[] xs = new double[1_000_003];
    double[] ys = new double[xs.length];
    for (int k = 0; k < xs.length; k++) {
      xs[k] = (k - 500_000) * 1e-3; // -500.0 to 500.002
    }
    exp(xs, ys);
    long differ = 0;
    for (int k = 0; k < xs.length; k++) {
      long want = Double.doubleToRawLongBits(StrictMath.exp(xs[k]));
      if (Double.doubleToRawLongBits(ys[k]) != want) {
        differ++;
      }
    }
    System.out.println(S.vectorBitSize() + "-bit vectors, " + xs.length
        + " inputs, results that differ from StrictMath's: " + differ);
  }
}

The NaN exception and the contract

  • In atan2, hypot and pow, a lane of two NaNs with different bits returns one of the two arguments' bits with the quiet bit set (for hypot, also with the sign cleared): see AGENTS.md, "Releases". The NaN counts are in strictmath-vs-libm/data/nantier-jdk-25.0.5.1.txt.

Boxing and the machine code

  • The allocation figures are exp's finish rows on common data in exp-xeon8573c-2026-11-21.txt.
  • CI's allocation check runs at 256 bits, the preferred species and SPECIES_MAX (read as allocation-free up to eight lanes only), and fails a row that reaches one byte per operation; 128 bits on x86 is known to box and is left out, and pow is held to a baseline, since StrictMath.pow allocates itself.
  • AsmTest (SKILLS.md, "The assembly check") reads what the JIT emits; its rule on calls holds from 256 bits up.

hypot's old words

  • For a subnormal argument fdlibm's hypot may scale both values by 2^1022 and keep reading the high words, the top 32 bits, it took before scaling; reading them again changes the result on some inputs. PROOFS.md's L16 has four such inputs and a count, and the lines are in this figure; the vector code keeps the old words, as the C does (HypotTest).

  • hypot-order.c calls Sun's C from reference/fdlibm-5.3/e_hypot.c (line 60 is the comparison quoted above), built with gcc 15.2.0 and -O0 -ffp-contract=off -fno-builtin -fno-strict-aliasing -D__LITTLE_ENDIAN: hypot(x, y) is …d062 and hypot(y, x) is …d063. HypotOrder.java gives …d063 for StrictMath.hypot and Math.hypot in both orders on JDK 17.0.21.1, 21.0.13.1 and 25.0.5.1. Both outputs are in strictmath-vs-libm/data/hypot-order.txt.
  • HypotPairs.java and HypotPairsEdges.java draw 1,300,000 pairs whose magnitudes share their high 32 bits, and hypot-order-check.c compares StrictMath with the C called with the larger magnitude first: they differ only on two pairs, both of two NaNs (the contract's exception). On these random pairs the C's own answer depended on the order only for pairs of two NaNs, so they test the rule less than the fuzzer's input does (strictmath-vs-libm/data/hypot-pairs.txt).
  • JDK-7130085, "Port fdlibm hypot to Java" (JDK 9, 2015), replaced the JDK's native C hypot with a Java port. The JDK's own tests, HypotTests.java at JDK 25, require hypot(a, b) == hypot(b, a). I ran only JDK 17, 21 and 25.

How the bits are kept

  • Ported from Sun's fdlibm 5.3 C sources only, never from OpenJDK's FdLibm.java (GPLv2 with the Classpath exception); StrictMath is only the oracle the tests call.
  • Where the code computes differently from the C, a numbered lemma in PROOFS.md argues the result is the same double for every input; the one place the code leaves the C, to match StrictMath, is hypot's argument order (the third surprise). Parts of those for exp, log and expm1 are machine-checked in proofs/, by an SMT solver on every pull request and under Z3 and cvc5 every night.
  • Tests compare every lane with StrictMath at every width the host has, on hard cases from Lefèvre's tables and CORE-MATH's MIT lists among others; each planted fault, a deliberate bug switched on in a test run, must be caught.
  • nightly.yml is set to sweep all 2^32 high words of every function, three low words each: on x86 at 256 bits, the widest species, and 512 bits when the runner has AVX-512; on Arm at 128 bits; at 128 bits on x86 a rotating 1/32 a night; one argument a night for a function of two. A fuzzer draws inputs from a fresh seed at every width.
